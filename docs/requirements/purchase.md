# 購買申請の初期業務要件（PoC入力）

この文書と `purchase-initial.json` は初回設計の入力・解釈結果を保存したものです。移行後の正本は `examples/purchase/contract.py` です。要件変更時に初期入力を追従更新する必要はありません。

## 業務

購買依頼部門の担当者（表示名：申請者）は、購買申請ID、取引先、正の整数の金額を指定して申請する。受付時には承認待ちとなり、IDと状態を返す。

申請者は申請に見積書A・Bを添付できる。本人の承認待ち申請だけを更新できる。2件を登録し、登録結果を返す。2件目が失敗したら今回の実行で作成したファイルを取り消す。他の実行のファイルは削除しない。取り消せなければ手動復旧が必要な状態を残す。

購買依頼部門の部門長（表示名：承認者）は承認または却下を行う。申請者本人による承認判断は禁止する。承認済み／却下済みの状態を返す。

承認後、指定日時にシステムが発注確定を開始する。購買部の発注担当者（表示名：発注担当者）による開始も同じ処理を利用する。却下時は発注を開始しない。

発注確定は別の業務単位として扱う。承認済み・見積書2件あり・未発注の場合に発注情報を作成し、申請を発注確定済みにする。両更新は同じDBトランザクションで行う。条件を満たさないときは発注しない。発注確定パイプラインは応答不要とする。

申請・添付・承認・発注の更新処理は、申請ID単位で排他する。競合時は拒否し、例外時にも解放する。

## AI・開発者による変換手順

1. 業務単位・ロール・情報・起動条件・処理・正常／異常結果を抽出する。
2. 固定IDと型を付与し、トリガーの入力元とパイプライン入力を対応付ける。
3. 不明点（例：ファイル種別や上限、承認期限、実S3の設定）は未決事項として残す。暗黙に補完しない。
4. 解釈した構造をレビューし、`purchase-initial.json` の形式で保存する。自然言語からの意味解釈はAI・人が担当し、構造からの生成を自動化する。
5. `python -m myworkflow.scaffold init <reviewed.json> <empty-directory>` で契約コード・型・未実装関数を生成する。
6. 実装を接続してテストし、コードから概要を再生成して元要件と照合する。

今回の初期入力にはステップIDや分岐など設計者の解釈が含まれます。自然言語だけを受け付ける汎用AIサービスや、意味の自動証明を実装したという主張はしません。
