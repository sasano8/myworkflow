# パイプラインの終了結果

## 共通の戻り値

パイプラインは `PipelineResult(code, messages)` を返す。申請ID、申請状態、発注IDなどの業務データは戻り値へ含めず、アーティファクトとして扱う。

```python
from myworkflow import PipelineResult, Message

PipelineResult(
    code=0,
    messages=(Message(level='info', text='申請を受け付けました'),),
)
```

```json
{
  "code": 0,
  "messages": [{"level": "info", "text": "申請を受け付けました"}]
}
```

| 項目 | 契約 |
| --- | --- |
| `code` | 0は正常終了。0以外は失敗。アプリケーション独自の非負整数で、HTTPステータスやOSの終了コードとは別 |
| 既定の失敗コード | 明示的なコードを持たない通常の例外は1 |
| `messages` | 重大度と文章の配列。Python上では `tuple[Message, ...]`。空も許可 |
| 重大度 | `info`、`warning`、`error`、`critical` |
| `ok` | `code == 0` を返す補助プロパティ。外部の結果データには含めない |

成功・失敗はコードで決める。警告付きの成功を表現でき、重大度だけでコードを変更しない。補償や後処理の失敗は、復旧が必要な障害としてコード1へ変更し、criticalメッセージを追加する。コードの大小は重大度を表さない。

## メッセージと例外の記述

通常のステップは引き続き `(ctx: Context) -> None` とし、アーティファクトをコンテキストへ書く。説明が必要なら `ctx.add_message` を使う。

```python
def submit(ctx: Context) -> None:
    ctx.services.submit(...)
    ctx.values['status'] = 'waiting-approval'
    ctx.add_message('申請を受け付けました')
    ctx.add_message('添付資料は後から登録できます', level='warning')
```

コードを持つ例外には `PipelineError` を使う。明示的な業務上の拒否には、その派生型の `BusinessError` を使う。

```python
from myworkflow import BusinessError, PipelineError

raise BusinessError(10, '発注条件を満たしていません', level='warning')
raise PipelineError(1001, '外部サービスの処理に失敗しました', level='error')
```

| 終了の原因 | 通常の呼出し元に返る結果 |
| --- | --- |
| 正常終了 | コード0と、処理中に追加されたメッセージ |
| `PipelineError` / `BusinessError` | 例外のコード・重大度・文章。先に追加したメッセージも維持 |
| コードのない例外 | コード1とerrorメッセージ |
| 補償・ロック解放・履歴保存の追加障害 | コード1。元のエラーの説明を残し、追加障害をcriticalメッセージとして追加 |

例外をコードへ変換する前に、既存の補償とロック解放を行う。一時障害のステップ再試行も先に行い、試行を使い切ってから失敗結果へ変換する。`KeyboardInterrupt` などの `BaseException` を通常の失敗結果には変換しない。

`PermissionError` や `ContractError` に独自のコードは割り当てていないため、現在は1となる。必要な業務コードは明示的に定義する。例外に偶然存在する属性からコードを推測しない。

## 呼出しAPIとアーティファクト

- `Engine.invoke(...)` は起動ロールと入力を検査し、通常の例外を終了結果へ変換する。
- `Engine.run_internal(...)` と互換名 `run(...)` は内部用で、受付認可を行わない。戻り値は同じ終了結果。
- `invoke_or_raise(...)` と `run_or_raise(...)` は、失敗を例外として扱うための明示的なAPI。成功時の戻り値は同じ終了結果で、業務データへ戻す互換APIではない。Temporal接続や例外を使うオーケストレーション、詳細な障害試験に使用する。

既存の `Pipeline.outputs` / SPECの `outputs` は、処理完了時に生成・保持できているべきアーティファクトのIDとして扱う。レスポンスのフィールドではない。最終的な存在・型の検査は維持するが、戻り値へコピーしない。コンテキストの値をDBへ保存したことまで自動保証するものではない。

後続処理が必要とするIDは、ワークフローが保持する入力、DB、オブジェクトストレージなどから明示的に渡す。購買サンプルの発注引継ぎは、戻り値から申請IDを取り出す方式をやめ、ワークフローが保持している申請IDを使う。

生成する `PSubmitResponse` 等は共通 `PipelineResult` の別名となる。リクエストは従来通り、パイプラインごとの型付きdataclassを生成する。旧い業務データ入りのレスポンス型を渡した場合はEngineの構築時に拒否する。

`reply=False` は外部への応答が不要という宣言であり、内部の実行管理は終了結果を受け取る。これによって業務アーティファクトの生成が禁止されることはない。HTTP応答や送信の抑制を行う汎用受付アダプタは未実装。

## 実行環境への伝達はアダプターの責務

パイプラインは実行環境に依存しない終了結果を作り、実行基盤向けのハンドラー（アダプター）が、その環境の成功・失敗・分岐へ変換する。ステップの業務ハンドラーがTemporalやプロセス終了を直接操作する必要はない。

例えば、プロセス実行なら共通結果を出力したうえで必要に応じて終了コード0／1へ変換し、Temporalなら返却またはApplicationErrorへ変換する。独自の業務コード1001等は構造化した結果に保持し、そのままOSの終了コードへ渡さない。業務拒否を分岐として扱うか、タスク失敗として扱うかも接続側の明示的な方針とする。Kestra用のアダプターはまだ実装していない。

## Temporalとの接続

Activityの名前は従来通り `myworkflow.pipeline`。パイプラインを実行し、成功または業務上の拒否なら共通終了結果の辞書を返す。

| 原因 | Activityの扱い |
| --- | --- |
| 成功 | code 0の結果を返し、Activity完了として記録 |
| `BusinessError`、かつ補償・後処理の追加障害なし | 非ゼロの結果を返す。Activity自体は完了し、Workflowが結果を判断する |
| 一時障害の試行枯渇、契約エラー、権限エラー、想定外の障害、その他の `PipelineError` | `ApplicationError` を送出。detailsの `result` に共通終了結果を含める |
| 業務上の拒否に補償・後処理の失敗が加わった場合 | 通常の拒否として返さず、Activityの失敗として伝える |

非ゼロの辞書を返すだけではTemporalはActivityの失敗と認識しない。そのため技術障害は例外で伝える。現在はパイプライン全体の安全な再実行を保証していないので、例外は `non_retryable=True` とし、サンプルのActivity試行回数も1を維持する。ステップ内の `RetryableError` に対する宣言回数の再試行は別に有効。

購買の手書きWorkflowは、Activityの非ゼロ結果を確認して後続処理を止める。このサンプルでは `BusinessRejected` としてWorkflowを失敗させる。すべての業務拒否を自動で別の状態へ遷移させる機構ではない。Workflow自身の返却形式と、パイプラインの共通終了結果も別の契約である。

## アーティファクトの確定

[ジョブIDによる準備・確定](artifact-jobs.md)を追加した。パイプラインの終了結果と、Coordinatorが保持する準備・確定状態は別に扱う。終了コードが失敗でも確定済みの場合があるため、結果不明時はジョブ状態を照会する。

## 文書と継続品質検査

業務概要の入出力列では「出力：終了コード・メッセージ」を示し、成果アーティファクトは別の列へ出す。

正規化した業務要件の形式をv2へ更新した。共通の `completion` 契約と、各パイプラインの `produces` を分け、従来のレスポンスを表したv1は暗黙変換せず拒否する。実行結果JSONや受入レポートのバージョンとは独立している。

旧い原文・解釈結果は保持し、旧品質入力・対応表・表示・レポートは `examples/apps/purchase/quality/legacy-v1/` に保存した。現在の回帰入力は `docs/requirements/purchase-completion.md`。合意した終了結果の変更と、明示的な共通契約の要件を追加したものである。

現行ケースは構造322項目、要件24単位。構造化10・概要のみ11・未表現3で、記載充足率は21/24（87.50%）。旧ケースの20/23から分母も変わっており、同じ原文に対する精度向上とは解釈しない。補償の所有範囲等の既知ギャップ3件は未解消のまま残す。
