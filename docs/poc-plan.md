# ゴール・品質基準・残課題

Pythonの業務契約からインターフェース・概要を生成し、実装・受入条件と固定IDで対応させる。概要だけから実装全体を復元することは目指さない。

## 合格・見直しの基準

| 観点 | 合格条件 | 見直す条件 |
| --- | --- | --- |
| 対応 | 必須入出力・処理・ロール・起動先が同じ宣言と実装に結び付く | 二重転記が必要、対応先が不明 |
| 再現性 | 型・順序・接続の不整合を意図的に入れると検査が失敗する | 出力一致だけで誤実装を見逃す |
| 業務条件 | 同じfeatureから文書とテストを作り、独立した保存先照会で検証する | 実装から期待値を作り直す、時計・障害で試験が不安定 |
| 変更 | 固定IDで追跡でき、再生成で手書き実装を失わない | 名称変更で対応が切れる |
| 保証 | 説明のみ・実装対応・自動検証・未検証を区別する | 補償漏れや誤削除、補償失敗を追跡できない |

詳細な状態機械・補償・復旧を概要表の外へ置くこと自体は見直し理由にしない。
完了した計画は掲載しない。検証根拠はテスト、[PoC評価](poc-evaluation.md)、[受入評価](acceptance-evaluation.md)、[往復品質](requirements-quality.md)を参照。

## バリューオブジェクトとデータ定義

- [ ] データ定義・状態グラフを含む総合的な往復品質指標と実案件レビュー。
- [ ] ドキュメントから新しい型定義を作る支援。任意の独自バリデーターの意味をSchemaから復元できるとはしない。

競合時は最新値と業務条件を再確認する。古い変更の強制上書きは行わない。読取り専用依存の整合性は書込み対象のバージョン検査とは別に検討する。
