# PoCのゴールとタスク

## 合意したゴール

業務要件からAI・開発者がインターフェースと実装の骨格を作り、実装後はコードを正本として業務概要を生成する。小さな実業務について「要件 → 骨格 → 実装 → 文書 → 要件変更」の一周が成立するかを確かめる。

最優先は、顧客向け概要に出る表層の契約とコードの対応である。概要ドキュメントだけから実装全体を完全復元することは目指さない。状態遷移の詳細、トランザクション、再試行などは内部実装・別ドキュメントに整理してよい。詳細な状態機械を概要表だけで表現できないこと自体を敗戦としない。

ただし、概要で約束した入力・出力・処理・担当ロール・起動経路などが、実装のどこに対応するか分からない状態にはしない。概要から省略した詳細は参照先と保証範囲を明示する。

## 表現と保証の境界

| 対象 | 今回確認する対応 | 詳細として分離できるもの |
| --- | --- | --- |
| パイプライン | 名前・固定ID・入力型・出力型・応答有無と呼出可能な関数 | 通信基盤固有の設定 |
| ステップ | 固定ID・概要・実装関数・実行順序 | 関数内の全ロジック |
| トリガー | 操作主体・起動先・入力の対応と受付アダプタ | スケジューラやイベント基盤の全設定 |
| アーティファクト | 情報の識別・型・参照／保持／永続化の区別とコード上の扱い | 全SQL・物理スキーマ・保存基盤 |
| ロール | 正式名・表示名・配置での割当と認可処理の参照 | 組織情報の取得や権限基盤の詳細 |
| 排他 | キー・範囲・競合動作と実装箇所 | 分散ロック基盤の詳細 |
| 待機・遷移 | 主要な待機・再開・引継ぎと対応する実装／詳細文書 | 状態機械全体・復旧・期限切れの詳細 |

対応の強さは「説明のみ」「実装への対応あり」「自動検証可能」を区別する。出力に載る説明文だけで実行時保証を主張しない。自然言語の業務概要の正しさはレビューが必要である。

## 合格条件

- 対象業務の必須入力・出力・ステップ・起動先は、同じ契約から骨格と概要を作れ、実装と対応付く。
- 型や順序、未接続の実装など、選定した不整合を意図的に入れると検査が失敗する。
- 代表的な正常系・異常系が、接続したコードの実行テストで確認できる。
- 要件変更後も固定IDで追跡でき、同じ契約の手作業による二重転記が不要である。
- トリガー・アーティファクト・遷移について、表現できた範囲、実装に接続した範囲、自動保証できる範囲を個別に報告できる。
- 顧客が概要から「誰が・何を契機に・何を扱い・何が確定するか」を確認できる。

## タスク

チェック済みは現状で確認済みのもの。未完了項目を既存の出力一致テストだけで完了にしない。

### P0-01 現状のベースライン

- [x] 宣言から決定的なMarkdown概要を生成する。
- [x] 固定ID、配置による流用、複数トリガー、ロールと表示名を表現する。
- [x] 購買申請・見積書添付・発注確定の宣言例を用意する。
- [x] Python 3.14のCI定義と、保存済み出力との完全一致テストを用意する。
- [ ] GitHub Actionsの実行結果を確認し記録する。

成果物：既存の宣言例・固定出力・テスト。現在のサンプルは処理を実行しない。

### P0-02 契約とコードの対応方式を決める

- [ ] 入出力のPython型、ステップ関数、辞書型コンテキストとの接続方式を定める。
- [ ] 固定IDから実装関数・定義箇所へ辿れる対応表を作る。
- [ ] 生成領域と手書き実装領域を分け、生成し直しても実装を失わない方式を決める。
- [ ] 表層の必須契約と、説明・詳細文書に委ねる事項をサンプルごとに分類する。

完了条件：契約一つの変更が型・骨格・概要のどこに反映されるか説明でき、契約の二重管理がない。

### P0-03 業務要件から骨格を生成する

依存：P0-02。

- [ ] 購買申請の元になる業務要件文書を、生成概要とは別に固定する。
- [ ] AIが要件を解釈する手順と、型・契約・骨格を出す形式を定める。
- [ ] 入出力型、ステップ関数、ロール割当、起動定義を生成する最小例を作る。
- [ ] 不明な要件と未実装処理を明示し、未実装関数が成功扱いにならないようにする。

完了条件：要件の必須契約を欠落なく骨格へ移せる。AIの自由文出力の一致ではなく、生成後の契約構造を検査する。

### P0-04 骨格と実処理を接続する

依存：P0-03。

- [ ] 申請受付、見積書保存、発注確定の最小処理を実装して接続する。
- [ ] 受付アダプタから入力を型付き契約へ渡し、コンテキストと出力へ接続する。
- [ ] 申請者・承認者の認可確認と排他処理を接続し、宣言と実装の対応を示す。
- [ ] アーティファクトの参照・保持・永続化を実コードへ対応付ける。

完了条件：正常系に加えて入力不正・権限不足・発注条件未達を実行で検出できる。使用した簡易保存基盤などの制約は記録する。

### P0-05 コードから概要を再生成し、不整合を検出する

依存：P0-04。

- [ ] 実装へ接続した契約から、顧客向け概要と実装対応表を生成する。
- [ ] 入力型不一致、出力型不一致、未接続ステップ、順序変更、誤った起動先を意図的に入れる試験を作る。
- [ ] 各試験が適切に失敗し、対象の固定IDが分かることを確認する。
- [ ] 固定出力の期待値更新はレビューで行い、テスト中には再生成しない。

完了条件：見た目の一致に加えて、実装との対応が壊れたとき検出できる。

### P0-06 要件変更の一周を検証する

依存：P0-05。

- [ ] 必須入力を追加し、型・実装・概要の更新を確認する。
- [ ] トリガーを追加し、パイプラインの流用と入力変換の対応を確認する。
- [ ] アーティファクトを改名し、固定IDと実装対応の維持を確認する。
- [ ] 承認経路を変更し、概要と詳細設計への反映範囲を記録する。
- [ ] 再生成で手書き実装が消えないこと、不要な二重転記がないことを確認する。

完了条件：変更前後の契約・実装・概要の差分とテスト結果を提示できる。

### P1-01 待機・状態遷移の表現範囲を調べる

依存：P0-02。P0の一周を妨げない範囲で進める。

- [ ] 承認待ち・時刻待ち・次ワークフロー起動を、実装または既存基盤へ接続する方式を試す。
- [ ] 概要には主要な境界を示し、詳細な状態遷移は別文書へ整理する。
- [ ] 概要・状態遷移文書・実装間を固定IDや参照で結ぶ。
- [ ] 再開、重複イベント、期限切れ、再試行のうち検証した範囲を明記する。

完了条件：完全な実行基盤の完成ではなく、表層との対応を維持できる範囲と限界が分かる。

### P0-07 実用性と継続方針を判定する

依存：P0-06。P1の未実施部分は未検証として記録する。

- [ ] 元の業務要件と生成概要を人が比較し、意味の欠落を確認する。
- [ ] 対応・自動検証・未検証の一覧と、各テストの結果を記録する。
- [ ] 下記の基準で、継続／範囲縮小／方式見直しを判断する。

成果物：評価レポート。全体の合否だけでなく、項目ごとの根拠と次のタスクを残す。

## 敗戦・見直しの定義

| 観測された問題 | 判定・対応 |
| --- | --- |
| 表層の必須契約を実行用と文書用に二重管理し続ける | 中核方式を見直す |
| 概要の処理を実装に辿れず、固定IDも対応を維持できない | 対応付け方式は不合格 |
| 選定した不整合を入れても検査が通る | その項目の自動保証は不合格。検査を修正する |
| 再生成で手書き実装が失われる | 骨格生成・更新方式は不合格 |
| トリガー・アーティファクトの必須契約が実装と結び付かない | 該当範囲を見直し、残る表層の価値を再評価する |
| 状態遷移の詳細を概要表だけで表現できない | それだけでは不合格にしない。別文書と実装への参照で補う |
| 長期待機や分散実行の自前実装が過大になる | 契約・骨格・概要生成へ範囲を絞り、既存実行基盤を利用する |

敗戦は全機能の破棄を意味しない。表層の契約対応が成立すれば、その範囲を独立したライブラリとして継続する価値がある。
