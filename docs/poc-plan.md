# PoCのゴールとタスク

## 合意したゴール

業務要件からAI・開発者がインターフェースと実装の骨格を作り、実装後はコードを正本として業務概要を生成する。小さな実業務について「要件 → 骨格 → 実装 → 文書 → 要件変更」の一周が成立するかを確かめる。

最優先は、顧客向け概要に出る表層の契約とコードの対応である。概要ドキュメントだけから実装全体を完全復元することは目指さない。状態遷移の詳細、トランザクション、再試行などは内部実装・別ドキュメントに整理してよい。詳細な状態機械を概要表だけで表現できないこと自体を敗戦としない。

ただし、概要で約束した入力・出力・処理・担当ロール・起動経路などが、実装のどこに対応するか分からない状態にはしない。概要から省略した詳細は参照先と保証範囲を明示する。

## 表現と保証の境界

| 対象 | 今回確認する対応 | 詳細として分離できるもの |
| --- | --- | --- |
| パイプライン | 名前・固定ID・入力型・出力型・応答有無と呼出可能な関数 | 通信基盤固有の設定 |
| ステップ | 固定ID・概要・実装関数・実行順序 | 関数内の全ロジック |
| トリガー | 操作主体・起動先・入力の対応と受付アダプタ | スケジューラやイベント基盤の全設定 |
| アーティファクト | 情報の識別・型・参照／保持／永続化の区別とコード上の扱い | 全SQL・物理スキーマ・保存基盤 |
| ロール | 正式名・表示名・配置での割当と認可処理の参照 | 組織情報の取得や権限基盤の詳細 |
| 排他 | キー・範囲・競合動作と実装箇所 | 分散ロック基盤の詳細 |
| 待機・遷移 | 主要な待機・再開・引継ぎと対応する実装／詳細文書 | 状態機械全体・復旧・期限切れの詳細 |

対応の強さは「説明のみ」「実装への対応あり」「自動検証可能」を区別する。出力に載る説明文だけで実行時保証を主張しない。自然言語の業務概要の正しさはレビューが必要である。

## 合格条件

- 対象業務の必須入力・出力・ステップ・起動先は、同じ契約から骨格と概要を作れ、実装と対応付く。
- 型や順序、未接続の実装など、選定した不整合を意図的に入れると検査が失敗する。
- 代表的な正常系・異常系が、接続したコードの実行テストで確認できる。
- 要件変更後も固定IDで追跡でき、同じ契約の手作業による二重転記が不要である。
- トリガー・アーティファクト・遷移について、表現できた範囲、実装に接続した範囲、自動保証できる範囲を個別に報告できる。
- 顧客が概要から「誰が・何を契機に・何を扱い・何が確定するか」を確認できる。

## 敗戦・見直しの定義

| 観測された問題 | 判定・対応 |
| --- | --- |
| 表層の必須契約を実行用と文書用に二重管理し続ける | 中核方式を見直す |
| 概要の処理を実装に辿れず、固定IDも対応を維持できない | 対応付け方式は不合格 |
| 選定した不整合を入れても検査が通る | その項目の自動保証は不合格。検査を修正する |
| 再生成で手書き実装が失われる | 骨格生成・更新方式は不合格 |
| トリガー・アーティファクトの必須契約が実装と結び付かない | 該当範囲を見直し、残る表層の価値を再評価する |
| 状態遷移の詳細を概要表だけで表現できない | それだけでは不合格にしない。別文書と実装への参照で補う |
| 長期待機や分散実行の自前実装が過大になる | 契約・骨格・概要生成へ範囲を絞り、既存実行基盤を利用する |

敗戦は全機能の破棄を意味しない。表層の契約対応が成立すれば、その範囲を独立したライブラリとして継続する価値がある。

## 追加タスク：分岐・補償と保証範囲

「補償」は、途中まで完了した外部への操作を取り消すための別処理を指す。複数サービスにまたがる処理を単一DBトランザクションと同じ意味でロールバックできるとは限らない。何を保証し、何が残り得るかも業務契約として整理する。

### P1-02 条件分岐を表現し、実装と対応付ける

依存：P0-02。結果はP0-07の項目別評価に含める。

- [x] 承認／却下、見積書あり／なしなどの分岐を代表例として定義する。
- [x] 条件、分岐先、合流先、どの条件にも一致しない場合の動作を定める。
- [x] 概要には業務上意味のある条件と結果を出し、詳細な判定ロジックは実装・別文書に整理する。
- [x] 分岐の固定IDから実装とテストへ辿れるようにする。
- [x] 各分岐と不一致時の経路を実行し、選ばれなかった経路の副作用が発生しないことを検証する。
- [x] 不明な分岐先や接続漏れを意図的に入れ、検査が失敗することを確認する。

完了条件：概要で示す条件・結果と、実際に選択された経路の対応を確認できる。すべての条件式を自然言語から完全復元する必要はない。

### P1-03 途中失敗時の補償を表現し、実行する

依存：P0-04、P1-02。Temporalの利用方法も検討するが、Temporalが外部操作を自動的に取り消すとは扱わない。

代表例：S3にファイルAを登録し、続けてファイルBを登録する。Bの登録が最終的に失敗した場合、業務方針に応じて今回作成したAを削除する。

- [x] 各ステップの正常終了、失敗、再試行、補償開始、補償完了、補償失敗を区別する。
- [x] 再試行で回復を試みる条件と、補償へ移る条件を定義する。却下などの業務分岐と技術的な失敗を分ける。
- [x] 正処理と補償処理の対応、適用条件、複数処理を補償する順序を定義する。
- [x] 作成したオブジェクトのキー・バージョンなど、補償対象を特定する記録を保持する。
- [x] 既存オブジェクトの上書き・他の実行による更新を考慮し、単純な削除で既存データを失わない方針を決める。
- [x] 成功応答を受け取れなかった場合も考慮する。実際にはBが作成済みかもしれないため、実行固有キーや冪等性、状態照会により残存物を判定・回収する。
- [x] intentの永続化と、停止済み実行を明示した手動復旧を実装し、子プロセスの突然終了後に確認する。
- [ ] キャンセル・タイムアウト時の自動復旧と、実行中処理との競合防止を検証する（次段階）。
- [x] 補償自体の失敗を隠さず、再試行・手動復旧が必要な状態として追跡できるようにする。
- [x] 補償処理の重複実行で追加の損失が起きないことを検証する。
- [x] 概要に「途中失敗時に何を取り消すか」を示し、詳細な復旧手順と実装へ参照を付ける。

完了条件：下記の障害注入試験で、副作用の残り方と復旧結果を検証できる。実S3を使わない試験と実S3で確認した範囲を区別する。実S3の資格情報がなくても、まず差し替え可能な保存アダプタで独立した検証を進める。

| ケース | 確認する結果 |
| --- | --- |
| A・Bとも登録成功 | 両方が残り、補償が走らない |
| Aの登録失敗 | Bを実行せず、存在しないAを成功済みと扱わない |
| Bが一時失敗し再試行で成功 | 両方が残り、不要な補償が走らない |
| Bが作成前に最終失敗 | 今回作成したAを補償し、補償完了を記録する |
| Bは作成済みだが応答が失われる | 曖昧な結果を解消し、方針に従ってA・Bの残存を処理する |
| A削除の補償が失敗 | 補償失敗と残存物を記録し、手動復旧または再試行へ進める |
| 同じ補償を再実行 | 他の実行や既存データを壊さず、安全に完了する |

### P1-04 保証する範囲を契約として示す

依存：P1-02、P1-03。未実装の保証をドキュメント上だけで達成済みにしない。

- [x] DBトランザクションで保証する範囲と、外部操作を補償で復旧する範囲を区別する。
- [x] 再試行、冪等性、補償の有無、補償不能な操作、手動復旧条件を整理する。
- [x] 一時的な部分完了が外部から見える可能性と、業務上許容する状態を定める。
- [x] 概要・詳細設計・実装・障害注入試験を固定IDで対応付ける。
- [x] P0-07の評価レポートへ、保証済み・対応のみ・未検証を追記する。

完了条件：「失敗したら元通り」という曖昧な約束ではなく、どの副作用をどの条件で取り消し、取り消せなければどう扱うか説明できる。

追加の見直し条件：失敗を成功扱いする、補償対象以外を削除する、補償失敗を追跡できない場合、その復旧方式は不合格とする。詳細な補償手順を概要表の外に置くこと自体は不合格としない。
