# 受入シナリオ・実行可能な業務要件のタスク

## ゴール

業務概要、受入シナリオ、実装を固定IDで結び、同じシナリオの正本から読みやすい説明と実行可能なテストを得る。概要からすべての受入条件を自動推測することは目指さない。AI・開発者が具体的な期待結果を定義する。

業務概要で全体像を共有し、受入シナリオと実装で細かい条件を潰す。[工程](development-process.md)に従い、開発移行後に顧客形式の業務要件を二重管理しない。

現在の通常テスト・Temporal結合テストはPythonで個別に書かれている。以下は未着手の追加タスクであり、既存テストが成功しているだけでは完了にしない。

## AT-01 シナリオの正本とpytest-bddの使い方を決める

優先度：最優先。依存：PoCのP0-02〜P0-06。

- [ ] Python宣言とpytest-bddのGherkinを比較する最小例を作る。Python 3.14で実行可能か確認する。
- [ ] シナリオID、関連する業務契約ID、事前状態、操作、期待結果、パラメータを定義する。
- [ ] パイプラインの処理ステップとGiven／When／Thenを区別する。同じ処理を複数の条件で検証できるようにする。
- [ ] シナリオごとの正本を一つに定め、文書・feature・Python定義を二重に手書きしない方式を選ぶ。
- [ ] 未定義の業務ID、操作・検証関数、重複シナリオIDを検出する方式を定める。

完了条件：同じシナリオから説明と実行へ接続でき、pytest-bdd採用／不採用の理由と生成方向を記録できる。

## AT-02 操作・検証をコンテキストへ接続する

優先度：高。依存：AT-01。

- [ ] シナリオ専用コンテキストと、業務ステップのコンテキストを区別し、受付入力・結果・実行IDを共有する。
- [ ] 申請者・承認者などの操作を、実際と同じEngineの受付契約へ接続する。
- [ ] 事前状態の準備、操作、独立したDB・保存先照会による検証関数を登録する。
- [ ] 型・事前条件・事後条件の検証と、業務全体の受入条件の分担を定める。
- [ ] 未実装の操作や検証は明示的に失敗させる。空の検証関数を成功扱いにしない。
- [ ] ケースごとのデータ分離・後片付けと、失敗時にも診断情報が残る仕組みを用意する。

完了条件：契約と同じ入口を使い、期待値を実装結果から作らず、実際の副作用を確認できる。

## AT-03 時間・対話・外部障害を制御できるようにする

優先度：高。依存：AT-02。

- [ ] 時計・イベント送信・待機状態の確認をテスト用アダプタへ分離する。
- [ ] 絶対日時とタイムゾーンを扱い、期限の直前・到達時点を再現できるようにする。
- [ ] 固定秒数のsleepで準備完了を推測せず、状態や実行履歴を待つ。待機には上限を付ける。
- [ ] Temporalの時間スキップ環境または制御可能な時計で検証し、実時間テストとの差を記録する。
- [ ] 信頼された受付によるロール付与と、ユーザー操作・重複イベント・権限不足を再現する。
- [ ] 保存失敗・応答消失・補償失敗を操作できるようにし、実S3と差し替えアダプタを区別する。

完了条件：長い実時間待機やブラウザ操作を必須にせず、同じ業務条件を再現できる。実際のHTTP・FE接続試験は別に管理する。

## AT-04 業務概要と受入シナリオを読みやすく出力する

優先度：高。依存：AT-01、AT-02。

- [ ] シナリオの正本から、顧客が読める前提・操作・期待結果の文書を生成する。
- [ ] 業務概要から関連シナリオへ、シナリオから対象の契約・実装へ辿れるようにする。
- [ ] pytest-bddを採用した場合はfeatureとScenario Outlineの具体例も出力対象にする。
- [ ] 業務ロールと、時計・障害注入などのテスト基盤の操作主体を区別する。
- [ ] 仕様の文書と、あるコミット・実行に対する合否のレポートを区別する。未実行を成功表示しない。
- [ ] 決定的な出力と表のエスケープを検証し、保存済みサンプルとの一致テストを加える。

完了条件：コードやテスト基盤の詳細を読まずに受入条件が分かり、生成文書を別の正本として編集する必要がない。

## AT-05 購買申請の代表シナリオを移行する

優先度：高。依存：AT-02〜AT-04。

- [ ] 承認前は発注0件、承認後も予定日時の直前までは0件、到達後に1件だけ確定する。
- [ ] 承認イベントが重複しても発注は1件のままになる。
- [ ] 却下・権限不足・見積書不足では発注されない。
- [ ] 見積書A/Bの登録成功、一時失敗後の成功、Bの最終失敗による打ち消しを確認する。
- [ ] 成功後の応答消失、補償失敗、手動復旧、他実行のファイル保護を確認する。
- [ ] 適切な既存テストを共通シナリオへ移し、低水準の契約・アダプタ試験は残す。

完了条件：各シナリオの説明と実行が同じ定義に由来し、選ばれなかった経路の副作用も検査できる。

## AT-06 要件変更と誤実装を検出する

優先度：高。依存：AT-05。

- [ ] 型・入力追加・名称変更など定義から導ける変更は、生成・整合性検査へ自動反映する。
- [ ] 業務上の期待結果が変わる変更はAI・開発者がシナリオを更新し、更新理由を残す。
- [ ] 早すぎる発注、重複発注、却下後の発注、補償漏れを意図的に入れ、対象シナリオが失敗することを確認する。
- [ ] 固定IDで改名・順序変更後も関連付けを維持する。
- [ ] 再生成で手書きのシナリオ・検証関数が上書きされず、期待値が実行結果に合わせて自動修正されないことを検証する。

完了条件：文書差分だけでなく振る舞いの誤りを検出できる。「差分を確認した」という記録だけを合格根拠にしない。

## AT-07 CIと評価レポートへ組み込む

優先度：通常。依存：AT-06。

- [ ] Python 3.14で通常の受入テストと文書一致検査をCIへ追加する。
- [ ] Temporalの受入テストは当面手動でオン／オフできるようにする。
- [ ] 合格・失敗・スキップ・未実行を区別し、業務契約ID・シナリオID・コミットへ対応付ける。
- [ ] 概要から確認できる条件と、未検証の条件を記録する。有限のシナリオですべてを保証したと主張しない。
- [ ] 顧客が生成した業務フローと受入シナリオ文書を使ってレビューできるか評価する。

完了条件：説明・実行・判定の根拠が結び付き、実行していないケースを保証済みと表示しない。

## 見直し条件

- 文書とテストに同じシナリオを手書きし続ける必要がある。
- 実装を壊しても受入テストが成功する。
- 実装から期待値を生成し、誤実装を正解にしてしまう。
- 固定IDで業務要件・受入条件・実装の対応を維持できない。
- 時計や外部障害の制御ができず、実行のたびに不安定になる。

これらが解消できなければ、シナリオの定義方式またはアダプタを見直す。pytest-bddを採用すること自体をゴールにはしない。
