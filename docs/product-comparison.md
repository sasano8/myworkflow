# 既存製品との比較とmyworkflowの存在価値

## 判断

myworkflowには、**Pythonで業務システムを作るチーム向けに、顧客向け業務概要・インターフェース・実装・受入テストの対応を保つライブラリ**としての可能性がある。ただし、現時点でその導入効果や市場需要は実証できていない。

フローをUIで作ること、宣言から実行すること、コードをGitで管理することは、既存製品が既に提供している。特にCamunda、Windmill、SpiffWorkflowは発想が重なる。独自のワークフローエンジンや汎用の画面作成製品として広く競う方針は勧めない。

存在価値が成立するかは、「既存製品や通常のPython開発に比べ、業務変更時の転記・対応確認・欠落修正の総コストが減るか」で判断する。文書を生成できたという技術PoCだけでは、この問いの答えにはならない。

## 調査範囲

調査日：2026-11-01。各製品の公式リポジトリのREADME、公式ドキュメントの公開ソースを確認した。参照先は末尾に記載する。価格、全エディションの機能差、実環境の運用性能は比較していない。セルフホスト・組込み・商用提供の条件は製品・版ごとに異なる。

製品の主な機能は資料に基づく。myworkflowとの適合性・強み・弱み・推奨方針は、本リポジトリの要件に照らした評価である。既存製品をインストールして同じ業務を実装した比較試験は未実施。「資料から本用途への適合を確認できない」ことを「その機能が存在しない」と読み替えない。

## UIで構築できる製品と、実行を支える基盤

| 製品・分類 | 主な定義方法とUI | 得意なこと | 今回の用途での比較点 |
| --- | --- | --- | --- |
| n8n [N] | ビジュアルなノード接続とカスタムコード | SaaS・API連携、イベントやAIを含む自動化、素早い組立て | 既存コネクタで足りる自動化では有力。Pythonアプリ内の契約・型・受入シナリオとの対応は別途設計する |
| Microsoft Power Automate [P] | フローデザイナー、テンプレート、コネクタ | Microsoft製品等との連携、承認、通知、クラウド／デスクトップ自動化 | 承認を含む社内業務をすぐ使いたい場合に有力。自社Pythonコードを正本にする狙いとは中心が異なる |
| Camunda 8 [C] | BPMN・DMN・FormsをModelerで定義し、エンジン・ワーカーへ接続 | 人とシステムをまたぐ業務プロセス、待機・イベント、タスク処理、運用確認 | 図と実行を対応させる強い代替。業務担当者が図を正本にしたいなら先に評価すべき |
| Windmill [W] | Python等のスクリプト、コードやYAMLのフロー、ビジュアルエディター、Git同期 | コードからUI・API・定期処理を提供し、フローや承認待ちを組み立てる | コード・UI・実行を兼ねるため直接競合に近い。コードファーストだけでは差別化できない |
| SpiffWorkflow / SpiffArena [S] | Python製エンジンがBPMNを実行。Arenaが図の編集・実行・監視を提供 | PythonとBPMNの組合せ、ループ・イベント・人を含む業務フロー | Pythonで業務の図と実行を一致させる直接的な代替。コードからの定義も持つため、単なるPython対応は優位性にならない |
| Temporal [T] | SDKのコードで定義。Web UIは実行の確認・運用が中心 | 長期待機、メッセージ、履歴・再生、障害に耐える実行制御 | UIでフローを作る製品とは役割が違う。myworkflowの実行基盤として組み合わせる候補 |
| Prefect [F] | Pythonのflow/taskとデプロイ定義。UIで実行を監視・開始 | データパイプライン、スケジュール、イベント、再試行、観測 | Pythonの処理連携・ジョブ管理が中心なら優先候補。顧客向けの業務契約表が必要かを分けて判断する |

myworkflowは、Pythonの契約宣言とコンテキストベースの処理を使う開発ライブラリのPoCである。編集UI、承認タスクの受信箱、組織管理、運用管理画面を持たない。上記の完成したプラットフォームと提供範囲・成熟度を同列には扱えない。

実行履歴から見える経路と、未実行の分岐を含む静的な業務概要は異なります。Temporal等を使っても外部副作用の冪等性・結果不明・補償は設計が必要です。既存製品との比較には、顧客向け表・型・受入条件を接続する追加コストも含めます。

## myworkflowの強み候補と弱み

| 観点 | 現在の強み・価値候補 | 弱み・裏付けが足りない点 |
| --- | --- | --- |
| 顧客との確認 | ロール、起動経路、入出力、過程の情報、固定IDを業務概要へ出す | 顧客による読みやすさ・合意形成の効果は未検証。現在の表が最適とは限らない |
| コードとの対応 | 型・接続・実装登録の不整合を検出し、同じモデルから型と概要を生成 | 宣言の説明とハンドラの意味までは同一化できない。書くメタデータが増える |
| 変更への追従 | 固定IDで履歴を保ち、ワークフロー層ではPythonのオブジェクト参照を使える | 購買の正本と内部参照はクラス・オブジェクトへ移行済み。宣言APIの安定性と他案件への適用は未検証 |
| 受入テスト | 同じGherkinから文書と実行を結び付ける | Gherkin、pytest-bdd、通常のPython開発でも実現可能。独自性は対応・導入コストの削減にある |
| 表現力の品質 | 原文の対応表と往復・型・欠損を別に検査し、未表現を報告する | 現在は小さな固定サンプル。原文の分割と対応表は人がレビューし、意味の証明ではない |
| 導入 | ライブラリとしてコードへ組み込める。データ契約にはPydanticを使用 | Python 3.14に限定。API、運用実績、移行・互換性、サポートが未成熟 |
| 実行と画面 | 既存Engineと任意のTemporal接続を試せる | 本番認証、分散排他、一般的な状態遷移実行、管理画面、コネクタ等は不足 |

強みの多くは、個々の技術の新規性ではなく、業務開発向けの組合せと使い方の提案である。既存製品が同じ検査や出力を拡張で提供することも可能で、技術的に模倣困難な優位性は現時点では確認できない。

## 誤った差別化を避ける

- 「UI製品はコードやGitを使えない」は誤り。少なくともWindmillはコード、IDE、Git同期を明示している。
- 「同じ定義から図と実行を得られるのが新しい」は誤り。BPMNを実行する製品は既に存在する。
- 「Pythonなら新しい」も不十分。SpiffWorkflowやPrefectが存在する。
- 「生成文書とコードが一致したので業務も正しい」は成立しない。意味、認可、状態保存、副作用は別に確認する。
- 「AIが要件を理解する機能がある」は現状の説明として不正確。現在の往復評価はレビュー済みの固定サンプルから始まる。

## 存在価値が生まれやすい顧客

有力なのは、顧客ごとに異なる業務を継続開発し、Pythonの既存コード、コードレビュー、CI、受入テストを既に使う受託・内製チームである。要件変更のたびに概要書やインターフェース表を追従更新し、漏れの確認に時間を使っているなら、本プロダクトを導入する理由がある。

提供価値の言い方は、「ワークフローを作れます」より「業務変更をコードに反映した後、顧客説明・インターフェース・受入条件の対応を崩さず確認できます」が適している。

一方、非開発者が自分で画面から設定したい、MicrosoftやSaaSの既存連携で完結する、すぐ使える承認画面と運用機能が必要、という場合は既存製品が有力である。データジョブの実行管理が主目的ならPrefect等、長期実行の信頼性が主目的ならTemporalの直接利用を先に検討する。

## 開発を続ける場合の重点

1. 顧客向け概要、型、実装、受入シナリオの対応を最優先にする。未接続・未検証・説明のみを隠さない。
2. Pythonのシンボル参照と固定IDを両立させ、要件変更時に書き直す量を減らす。宣言の学習やメタデータ記述の負担も測る。
3. 状態・遷移はまず業務説明と検査に必要な範囲に絞る。実行の整合性が必要な箇所は検証し、汎用の永続実行基盤を自作しない。
4. Temporal等の既存基盤を使う。Camunda・SpiffWorkflow等との連携は候補として比較し、対応済みとは主張しない。
5. 新しい業務でも、原文 → 契約 → 型 → 概要 → 受入結果の対応を確認する。小さな購買サンプルの高い一致率だけで評価しない。

### UIを作る場合

宣言から生成する[閲覧用の業務図](../examples/feature_demos/declarative_review/docs/flow.md)を追加した。顧客が表より図を理解しやすいかを確認でき、正本を増やさずに済む。

編集まで扱う場合は、編集できる宣言の範囲を限定し、UI操作を契約の変更候補として出力し、ID・型・接続・シナリオの検査とレビューを通す。自由なPythonコードをUIへ読み込み、全ての表現を損失なく編集して戻すことは別の難題である。対応外のコードを黙って落とす仕組みは作らない。

UIそのものを主要価値にするなら、既存Modelerやフロー製品を採用する案と先に比較する。

## 続行・縮小・撤退を決める評価案

以下は今後の評価案であり、達成済み・顧客合意済みの基準ではない。

| 評価 | 実施方法 | 続行の根拠／見直し条件 |
| --- | --- | --- |
| 比較相手 | 通常のPython＋型定義＋Gherkin＋文書テンプレートと比較し、案件に適したCamunda・Windmill・SpiffWorkflow等の一つとも比較する | 追加ライブラリを導入する効果が、既存の組合せを上回るか |
| 業務の幅 | 独立した実務の候補を3件程度選ぶ。差戻し、時刻・イベント待ち、補償を含める | 一つのサンプルに最適化しただけなら用途を狭める |
| 変更コスト | 入力追加、ロール変更、承認経路変更、差戻し追加、補償条件変更を同じ要件で実施する | 契約・実装・文書・テストの更新と検証を含む総時間が減るか。学習・初期導入は別に記録する |
| 効果の目標例 | 上記の変更作業の中央値を比較し、例えば30%以上の短縮を仮の目安とする | 数値は評価前に合意する。現時点では短縮の実測値なし |
| 対応の品質 | 必須項目の欠落、未接続、誤った型・起動先・遷移先を意図的に入れる | 選んだ不整合は全て検出し、未表現・説明のみを正直に残す。単なる出力一致へ退行したら見直す |
| 顧客の理解 | 生成物から担当者、契機、入出力、成功状態を説明してもらう | 元の資料と同等以上に確認できるか。読めずに別資料の二重管理が戻るなら不合格 |
| 記述負担 | 概要・条件・実装・シナリオの転記箇所、宣言のためだけのコード量、修正漏れを記録する | 対応管理のために増える作業が、削減する作業を上回るなら縮小する |
| 実行の整合性 | 状態保存と副作用の間に障害を入れ、重複・応答消失・補償失敗を確認する | 図と文書だけ整い実データが矛盾する場合、実行可能な契約としては不合格 |
| 継続利用 | 初回担当者以外が変更し、次の案件でも使いたいかを確かめる | 作者しか保守できない、採用・保守の意思がない場合は独立製品化を再考する |

効果が文書生成・差分検査に限られるなら、実行機能を縮小して生成・検査ライブラリとして続ける選択がある。既存製品への薄い拡張で同等の効果を得られるなら、その拡張へ転換する。既存の型・テスト・テンプレートで十分なら、このプロダクトを増やさない判断も妥当である。
