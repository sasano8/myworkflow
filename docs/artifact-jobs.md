# アーティファクトの準備と確定

ArtifactCoordinatorは保存・確定のProtocolです。中間サーバーは用意せず、現在はTemporaryArtifactCoordinatorで実装します。[実行例](../examples/feature_demos/prepared_approval/application.py)。

## ジョブの約束

| 操作 | 契約 |
| --- | --- |
| read(key) | 確定済みの値とバージョン。未登録はNone |
| prepare(job_id, writes) | 準備を永続化し、確定値は変えない |
| commit(job_id) | 想定バージョンを検査し、全変更と確定結果を一括公開 |
| status(job_id) | 準備・確定・破棄と確定バージョンを照会。未登録はNone |
| discard(job_id) | 未確定の準備を破棄し、そのジョブのファイルを削除 |

宣言のArtifact IDは情報の種類、保存keyは個別の対象、job_idは一件の確定依頼を識別します。同じ依頼の再送は同じID、別の操作は新しいIDを使い、試行ごとのIDへ変えません。Context.run_idを別のタスクへ引き継ぐ際も明示します。

同じID・内容のprepareは現在の状態を返し、内容違いはJobConflictです。commitの再送は最初の結果を返し、バージョンを再加算しません。後続更新でも過去の結果は変わりません。破棄は再実行できますが、確定済みの破棄・破棄済みの確定・最終状態の準備状態への巻戻しは拒否します。

## 楽観ロックと排他ロック

ArtifactWrite.expected_versionは0で新規作成、正数でそのバージョンからの更新です。排他は同時処理を待機・拒否し、楽観ロックは判断後の更新競合を検出します。併用できます。

| 順序 | 操作A | 操作B |
| --- | --- | --- |
| 1 | バージョン1を読む | バージョン1を読む |
| 2 | 想定1で承認を準備 | 想定1で却下を準備 |
| 3 | commit成功、バージョン2 | — |
| 4 | — | ArtifactConflict。変更は一件も反映されない |

競合した準備は照会・破棄できます。再判断は最新値・業務条件を確認し、新しいジョブIDを使います。古い変更のバージョンだけを変えて強制適用しません。検査対象は書込みキーだけで、読んだだけの別データは含みません。

高水準APIは[ctx.changesと遷移検証](transition-execution.md)を使います。低水準APIを直接呼ぶ書込みへ契約検査を自動適用するものではありません。

## デフォルトの一時領域

保存先は `tempfile.gettempdir()/myworkflow-artifacts/<namespaceのSHA256>/`。rootで親を変更できます。同じroot・namespaceなら別プロセスから参照でき、オブジェクト破棄では削除しません。別ホスト・コンテナへ自動共有せず、OSの清掃で消えるため長期待機・本番には保持できる保存先が必要です。

SQLiteには業務JSON・状態・準備・確定結果・ファイル参照を保存し、blob本文はジョブ別ファイルへ置きます。論理ID・名前をそのままパスへ使いません。ファイル保存のために本文をDBへ変換しません。

## blobの所有と公開

BlobRefはjob_id・論理名・SHA256・サイズを持ち、ArtifactWrite.valueへ渡します。任意のパスをJSONに書いただけでは管理対象になりません。stage_fileは元ファイルを変えずコピーし、stage_streamは1MiBずつ処理します。独自の固定サイズ上限はありませんが、ディスク・保存基盤の制約は残ります。

prepare前にステージでき、その時点のstatusはNoneの場合があります。list_filesで一覧を確認でき、prepare後の追加は拒否します。同名・同内容の再送は同じ参照、異なる内容はエラーです。他ジョブ所有の参照の公開も拒否します。

commit前に存在・サイズ・SHA256を検証し、大きいファイルの検証はDBトランザクション外で行います。commit時にファイルを移動せず参照を公開します。信頼された処理は公開前もopenできます。openはメタデータ・サイズを確認し、公開後のSHA256照合はverifyを明示します。管理外の改変は防ぎません。

discardはDBへ破棄を記録してからファイルを削除し、中断後も再実行できます。prepare前のファイルも回収できます。確定済みファイルは自動削除しません。

## 保証する保存境界

短いBEGIN IMMEDIATE内で全バージョンを検査し、同じSQLite内の業務JSON・状態・公開参照・確定結果を一括反映します。prepareからcommitまでロックを保持しません。DB単位のロックで、キー単位のアドバイザリーロックではありません。

ファイルを先に完成させて参照を確定する方式です。作成後のメタデータ保存失敗で未参照ファイルが残る場合はdiscardで回収します。外部DB・S3・メール・既存購買DBを含む原子性はありません。購買の補償モデルは[別の保存方式](execution-design.md)で、Coordinatorへ暗黙に移行していません。旧body列の内容も暗黙移行せず、明示的なエクスポートを要求します。

Engine履歴も別境界です。commit後に応答・履歴保存が失敗したらstatus(job_id)を照会し、準備済みは同じ内容で確定または破棄、確定済みはその結果を採用します。これはProviderの復旧で、同じrun_idを拒否するEngine全体の自動再開ではありません。Providerは信頼された呼出し元向けです。

## 保持・削除ポリシー（未実装）

| 用途 | 方針 |
| --- | --- |
| DB反映用の一時データ | 確定済みで復旧不要となってから削除。反映先の業務データは保持 |
| 正式保管ファイル | 自動削除対象外 |
| 一時アップロード | 用途ごとの起点・期間で期限切れを判断 |
| 失敗・補償待ち・結果不明 | 期限だけで消さず復旧判断まで保留 |

保持条件は業務宣言、対象判定と削除はProvider、実行周期はcron・Lifecycle等が担います。昇格時は保持方針も変更し、参照追加・昇格とGCの競合を扱います。実体と確定結果・冪等性記録・削除履歴は保持期間を分けます。管理情報の削除は再送・結果照会の保証期間に影響します。[実装・試験の残課題](poc-plan.md#アーティファクトの保持削除ポリシー未着手)。
