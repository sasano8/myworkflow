## 課題：AIの要件変更をアノテーション中心の開発へ統一する

推奨優先度：高。既存課題があれば本内容を反映し、重複作成しない。

### 問題と原因

Webアプリ要件の変更時、AIが手書きMarkdownを更新し、注釈付きコードへの反映を後回しにした。カタログを追加した後もREADMEが要件の別正本として残り、テストはMarkdownのIDを読み取って参照の存在だけを確認していた。「中心となる業務」の区分もコード宣言ではなく説明文だけに持っていた。

文書の存在を完了条件とし、要件の正本・編集先・生成手順が作業規約と検査で固定されていなかったことが原因。カタログが存在するだけでは、AIが注釈を使うとは限らない。

### 今回の対策

- [x] Webアプリの合意済み要求をrequirements.pyの`@requirement`へ移す。ID・名前・概要・中心／周辺の区分を宣言する。
- [x] 画面の名前・説明は同じ注釈から読み取り、Markdownから仕様を読み戻さない。
- [x] 要求カタログを注釈から自動生成し、READMEは概念と参照先、未決事項は検討メモへ分ける。
- [x] 注釈の登録漏れ・重複、画面やステップへの参照欠落・未知の要件IDを生成時に検査する。異常を入れたテストも追加する。
- [x] AGENTS.mdに「要件変更は注釈から始める」「Markdownだけで完了としない」「生成・関連検査まで行う」を定める。

規約は判断を誘導するもの、検査は検出可能な構造違反を止めるもの。いずれも意味の完全一致は保証しない。

### 残タスクと完了条件

- [ ] AI向けの実例・開発ガイドテンプレートに、要件受領 → 注釈変更 → 生成 → 差分・検査結果確認の手順を含める。
- [ ] 要件変更なのに注釈差分がないケースを、AIの変更サマリーとコード差分で検出・レビューする方式を設計する。READMEのリンク修正など、正当な文書だけの変更を一律禁止しない。
- [ ] 追加・削除・名称変更・中心／周辺の変更を依頼する評価ケースを作り、注釈・生成文書・参照が一緒に変わるか確認する。
- [ ] 既存の要求IDの説明と実装が食い違うケースを、独立した受入条件で検出する。IDの参照検査だけで成功としない。
- [ ] AIが出力する完了報告に、変更した宣言・生成物・検証結果・未表現の要件を含める。正しく表せない要件を無言でMarkdownへ逃がさない。
- [ ] Linear接続後、既存プロジェクト・既存課題を確認して登録先URLを本課題へ追記する。

評価では、依頼した意味が維持されたかは人または独立した受入条件で確認する。生成物一致率だけをAIの遵守率や業務要件の充足率として扱わない。
