# PoC評価

## 判断

表層の契約をコードと対応付ける方針は、今回の小さな購買業務では成立した。要件の解釈結果から型と骨格を生成し、手書き処理を接続し、同じ契約から業務概要を生成し、変更と不整合を検査する一周を実装した。契約・文書生成ライブラリと、Temporalへの任意アダプタとして継続する。

これは対象業務を限定した技術PoCの結果である。顧客・人による業務概要の妥当性レビューは未実施。汎用的な自然言語理解、本番運用基盤、実S3、分散ロックを完成させたという判定ではない。

## 実施したチェック

Python 3.14.8で通常37テスト、Temporal結合5テストが成功。通常テストには元の宣言専用モデル12件も含む。初期の表と実行版の表の2種類について、保存済み出力との完全一致を確認した。未実装部分をスキップして合格扱いにする仕組みは使っていない。

| 項目 | 根拠 | 判定 |
| --- | --- | --- |
| 要件から骨格 | 初期要件・レビュー済み構造を固定し、scaffold initで契約・dataclass・登録済み未実装関数を生成 | 構造からの生成は合格。自然言語解釈はAI・人の作業 |
| 未実装の検出 | 生成骨格の関数を呼ぶとNotImplementedError。実装ID未接続も拒否 | 合格 |
| 型と実装の接続 | 生成型と契約の照合、受付／ステップ前後の値の型検査 | 合格（フラットな基本型） |
| 実処理 | SQLiteへ申請・添付・発注を保存し、発注確定まで実行 | 合格（簡易基盤） |
| 認可と排他 | 起動ロール、本人の添付、自己承認禁止、競合拒否、例外後のロック解放 | 合格（信頼されたPrincipal・単一Services内） |
| 文書とコード | 同じProgramから概要・型一覧・起動対応・実装関数対応表を生成 | 合格 |
| 不整合の検出 | 入出力型の差、欠けた実装、未知の起動先／遷移先、入力変換の不足、未生成情報を読む順序変更、分岐の欠落を注入 | 対象とした不整合は検出 |
| コンテキスト | 未宣言の読取り／書込み、不正な出力型を注入 | 検出。サービス内部の全I/O解析は対象外 |
| 必須入力の追加 | 依頼部門を追加。古い型は拒否、型再生成・処理の更新後は受理され、実装が値を読んだことを確認 | 合格 |
| トリガー・ロール変更 | 別の入力元から同じ処理へ接続、承認ロール変更で以前のロールを拒否 | 合格 |
| 改名・ID維持 | アーティファクトの表示名変更後も実装と行の固定IDを維持 | 合格 |
| 実装の保護 | 既存ディレクトリへの初期生成拒否。型再生成後も手書きファイルが同一 | 合格 |
| 分岐 | 承認／却下、発注可／不可。非選択処理をスキップして副作用がないことを確認 | 合格（bool条件の線形合流） |
| 補償 | A/B成功、A失敗、B一時失敗、B最終失敗、応答消失、補償失敗・再開、別所有者の保護 | 合格（SQLiteの保存アダプタ） |
| DB原子性 | 発注挿入後に障害を注入。発注作成と申請更新の両方が残らない | 合格 |
| 停止後の手動復旧 | 子プロセスをos._exitで停止し、残ったintentから別Servicesで回収 | 合格（停止済みと確認した明示的な復旧） |
| Temporal | 同じEngineで申請・添付・承認・発注。待機中のWorker再作成、重複Signal、Timer、Child Workflow、却下、権限不足 | 合格（開発サーバー） |
| インストール | Python 3.14の仮想環境へライブラリをeditable install | 成功 |
| CI | 通常チェックと任意のTemporal手動ジョブを定義 | リモートの実行結果は未確認 |

テストの詳細は `tests/runtime/test_engine.py`、`tests/contracts/test_models.py`、`tests/adapters/temporal/test_purchase.py` にある。障害注入は実際の保存結果・状態・件数を検査し、出力一致だけを実行の証拠にはしていない。

## 初期要件との一次照合

AIによる照合では、申請者・承認者・発注担当者、正の金額、本人の添付、別人承認、承認／却下、日時／手動の起動、見積書2件、発注確定、途中失敗時の打ち消しを契約または実装へ対応付けた。

待機・詳細遷移は概要だけへ押し込まず、[実行設計](execution-design.md)とTemporalコードに分離した。HTTPサーバーと実ブラウザは作らず、受付アダプタへの辞書入力で入力変換を検証した。Temporalでは日時起動を実行し、手動トリガーはローカルEngineの変換・ロール検査までを対象とした。

概要の文章が業務に適切か、ロールの正式名が顧客組織に合うかは顧客レビューが必要である。こちらの検証だけで顧客合意済みとはしない。

## 保証範囲

- 同じ契約から型・概要・実行順序を得る。実装関数と固定IDの接続は検査する。
- ステップ内部の業務判断やDB操作の正しさは、型だけでは保証しない。サンプルの機能試験で確かめた範囲に限る。
- 保存の補償は部分完了が見える期間をなくさない。登録前にintentを残し、今回の実行の所有者・バージョンが一致した物だけを回収する。
- 補償失敗はmanual-recoveryとして残す。認可済みの運用者が復旧する想定で、運用画面は未実装。
- 再試行は宣言された一時障害だけ。Temporal Activity全体の自動再試行は無効にし、二重実行を安全だと見なさない。
- Temporalサーバーの再起動、Activity途中の停止、キャンセル・タイムアウト時の自動補償、長期履歴の移行は未検証。
- 実S3の資格情報・通信・API・削除条件は未検証。保存アダプタのモデルで検証した。
- 本番認証、外部組織の認可、分散排他、添付の置換・バージョン更新は未対応。

## CIの観測

ローカルで通常のCIと同等のテスト・出力比較・購買フローを実行した。GitHub Actionsの実行結果取得は `api.github.com` への通信がForbiddenとなり確認できなかった。Gitの読み書きが成功することと、GitHub APIへアクセスできることは別である。CI成功とは報告しない。

Temporalはpush時には起動せず、手動実行の `temporal` 入力を有効にした場合だけ動く。手動ジョブのリモート実行も未確認。

## 次の判断

PoCの中核である表層の対応は、今回の対象では継続可能と判断する。以下は次段階とする。

1. 顧客による生成概要のレビュー、GitHub Actionsの実行結果確認。
2. 実S3アダプタで所有権・バージョン・曖昧な成功・補償の試験。
3. 認証済みのHTTP／Signal受付と、実際の組織ロールの接続。
4. 分散排他、Activityの冪等性と途中停止の復旧、期限切れ・キャンセル。
5. 条件式・ネストした型・並列実行など、必要な表現だけを追加する。

概要と実装の手作業による二重転記が再び必要になる、または対応を壊しても検査できなくなる場合は、この判断を見直す。複雑な状態遷移を別文書へ分けたこと自体は敗戦としない。
