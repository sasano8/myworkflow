# リファクタリング計画

## 目的と進め方

PoCで確認した「契約コード → 業務概要・型」「受入シナリオ → 文書・実行」の対応を維持し、購買業務・保存方式・実行基盤を差し替えられる構造へ整理する。

最初は振る舞いを維持するリファクタリングを行う。PostgreSQLのアドバイザリーロック、実S3、本番認証、完全なクラッシュ復旧は機能追加として区別する。SQLiteにキー単位のアドバイザリーロックがあるとは扱わない。

すべてのタスクは未着手。各タスクを小さな変更に分け、固定ID、受入条件、失敗の扱い、手書き領域の保護を確認して進める。既存の顧客向け概要・受入シナリオを移行の判断基準にする。

## 現状の課題

| 箇所 | 確認した構造 | 整理する理由 |
| --- | --- | --- |
| myworkflow/__init__.py | 宣言モデル・検証・Markdown生成を同居 | 公開APIと内部の役割を分離する |
| myworkflow/executable.py | Programの辞書解釈・検証・Catalog変換・文書生成、Engine、型生成を同居 | 定義の二重構造と責務の集中を減らす |
| Program.spec | 呼出側が渡した可変辞書を保持 | 検証後の変更による実行・文書の食い違いを防ぐ |
| Engine | services.begin／record／lockへ暗黙に依存 | 必要な基盤機能を明示して差し替える |
| examples/purchase/services.py | 業務SQL・模擬オブジェクト保存・ロック・履歴・補償・障害注入を同居 | 業務処理とテスト用機能を分ける |
| 現在のロック | 同一Services内のスレッドロック | 複数インスタンス・プロセスへの保証を混同しない |
| scheduling.py / temporal_workflow.py | 業務ID、実行ID、受付payloadの組立てを個別に記述 | 同じ業務の接続方法のずれを減らす |
| myworkflow/acceptance.py | Gherkin読取り・pytest-bdd登録・購買向けタイトル・レポート表示を同居 | 他のサンプルでも利用できる境界にする |
| tests/conftest.py | 全体のpytest起動時に購買シナリオを読込み、ケース選択・結果を収集 | ライブラリ試験をサンプルの存在や任意依存から切り離す |
| acceptance/catalog.py | 実装ハッシュ対象のファイルを手書き列挙 | ファイル移動や新アダプタ追加時の検証漏れを減らす |

## 優先順位と順序

| 段階 | タスク | 狙い |
| --- | --- | --- |
| A：変更前の基準 | RF-00 | 互換性・比較対象を固定する |
| B：定義と実行の境界 | RF-01 → RF-02 → RF-03 | 契約・公開API・実行への接続を整理する |
| C：基盤の差替え | RF-04、RF-05 → RF-06 | ロック・保存・履歴・補償の責務を分ける |
| D：業務と基盤の接続 | RF-07 → RF-08 | サンプルとTemporalの接続を整理する |
| E：受入と生成物 | RF-09 → RF-10 → RF-11 | pytest・文書・結果の生成を整理する |
| F：利用側での確認 | RF-12 | 第二の小さな業務で購買依存がないことを確認する |

RF-04とRF-05はRF-03後に別々に進められる。大規模な一括移動は行わず、公開APIの互換窓口を残しながら段階的に移す。

## RF-00 互換性と比較基準を固定する

優先度：最優先。依存：なし。

- [ ] 公開API、契約の入力形式、固定ID、実行結果、エラー、生成物の互換性方針を記録する。
- [ ] 通常テスト、受入12ケース、任意のTemporal受入2ケース、既存Temporal結合5件の変更前の結果を記録する。
- [ ] 既存の4変異試験（早期発注・重複発注・却下後発注・補償漏れ）を維持する。
- [ ] 生成文書の意味・順序・固定IDと、手書きファイルを上書きしないことを比較対象にする。

完了条件：変更前の振る舞いと未保証の範囲が分かる。モジュール移動による実装パス・リンクの変更は、意味の変更と区別してレビューできる。

## RF-01 宣言モデルを統一し、読取り後の契約を不変にする

優先度：高。依存：RF-00。

- [ ] 辞書のSPECを入力形式として残し、検証済みの型付きモデルへ一度だけ変換する。
- [ ] 既存のCatalog系モデルとProgramの辞書構造について、実行・生成が読む共通モデルを決める。
- [ ] 省略値を正規化し、検証後は元の辞書を書き換えてもモデルが変わらないようにする。
- [ ] ワークフロー・配置・トリガー・ステップ・補償のIDと参照を共通に扱う。
- [ ] 初回要件の履歴データと、コード移行後の正本の区別を維持する。

完了条件：実行・型生成・概要生成が同じ検証済みモデルを読み、移行用の変換を除いて契約を二重に管理しない。

## RF-02 検証とエラーを整理する

優先度：高。依存：RF-01。

- [ ] 構造、ID・参照、型、データフロー、起動定義、実装接続の検証を分ける。
- [ ] 不正なSPECで素のKeyError／TypeErrorが漏れるケースを洗い出し、対象ID・項目・理由を持つエラーへ揃える。
- [ ] bool条件の変更・再代入、条件付き生成値、両経路の合流に対する現在の静的検証の前提を定める。
- [ ] 同じ入力項目や参照の重複、生成名の衝突、未知の操作種別を一貫して検査する。
- [ ] 実装レジストリの直接書換えを減らし、登録・検索・テスト用差替えのAPIを用意する。

完了条件：不整合を意図的に入れた検査が引き続き失敗し、どの契約を修正すべきか分かる。分岐表現の拡張は別タスクとする。

## RF-03 実行エンジンの基盤依存を明示する

優先度：高。依存：RF-01、RF-02。

- [ ] Engineが必要とするLockProvider、ExecutionStoreなどのProtocolを定義する。
- [ ] Contextを、宣言された値、業務用の依存、実行メタデータへ整理する。
- [ ] 認可済み受付と、低水準のパイプライン実行をAPI上で区別する。
- [ ] 入出力検証、ステップ実行、再試行、補償、終了処理を小さな内部処理へ分ける。
- [ ] 空パイプラインや出力検証失敗でも、最後のループ変数に頼らず正しい失敗箇所を記録する。

完了条件：Engineが購買のServicesやSQLiteを知らずに実行できる。認可を通さない内部APIが公開受付と混同されない。

## RF-04 ロックを独立させ、保証範囲を明示する

優先度：高。依存：RF-03。

- [ ] 現行のスレッドロックをInProcessLockProviderとして抽出する。
- [ ] 名前空間、アーティファクトID、型付きの値からロックキーを作る規則を定める。組立て順序やPythonのランダム化hashに依存させない。
- [ ] 取得、競合時の拒否／待機、タイムアウト、再入、解放の契約を定める。
- [ ] 業務上の排他とDBの原子性・一意制約を区別し、文書へ反映する。
- [ ] 同じProviderの共有時、別インスタンス、例外、補償、解放失敗を検証する。
- [ ] DBトランザクションを承認待ちやS3通信のために長時間保持しない。業務ロックを外部I/Oまで保持する必要がある場合は別の設計判断として記録する。

完了条件：単一プロセスのロックを分散排他と誤認せず、Providerを差し替えてもキーと競合動作を説明できる。PostgreSQL実装はEX-01へ分離する。

## RF-05 購買の保存処理と障害注入を分離する

優先度：高。依存：RF-03。

- [ ] 購買Repository、ObjectStore、補償用のintent記録、実行履歴を分離する。
- [ ] SQLiteのトランザクション境界を保存層へ集約し、発注作成と申請更新の原子性を維持する。
- [ ] 障害注入と呼出回数の観測をテスト用のラッパーへ移す。
- [ ] 現在の模擬オブジェクト保存を、実S3と区別できる名前と構成にする。
- [ ] 準備・操作は業務API、期待結果は独立した照会を使う受入試験の境界を維持する。

完了条件：業務処理が保存方式や障害注入の内部に依存せず、トランザクション試験と保存障害試験が引き続き成立する。

## RF-06 再試行・補償・履歴の責務を分離する

優先度：高。依存：RF-03、RF-05。

- [ ] 補償の登録、実行順序、成否を専用の実行状態として扱う。
- [ ] 失敗した処理も補償対象になり得る現行の方針を維持する。
- [ ] 補償関数が必要とする記録・コンテキストと、通常のステップの読書き契約の関係を定める。
- [ ] 実行履歴の書込み失敗、補償失敗、ロック解放失敗が重なった際に、元の失敗を失わないエラー構造にする。
- [ ] completed、failed、manual-recoveryなどの状態を型付きで整理し、正常完了後の再利用・復旧を拒否する。
- [ ] 手動復旧の判断と対象確認を分離し、実行中処理を不用意に復旧しない入口にする。

完了条件：逆順補償・応答消失・別所有者保護・繰返し復旧を維持する。自動クラッシュ検知や完全復旧の保証はEX-03に分離する。

## RF-07 サンプル業務から固定値と接続の重複を減らす

優先度：高。依存：RF-03、RF-05。

- [ ] ScheduledPurchaseの申請ID、実行ID、対象配置、ロール取得を引数・解決関数へ移す。
- [ ] 配列の0番目・2番目や最初のトリガーへの依存を減らし、固定IDで定義を検索する。
- [ ] 起動payloadの変換、次ワークフローの解決をローカル実行とTemporalで共用できる形にする。
- [ ] 業務シナリオに必要な固定データはfixture側に残し、業務実装へ混ぜない。
- [ ] 複数の申請を同じServices内で扱い、実行ID・ロックキーが干渉しないことを確認する。

完了条件：purchase-001だけで動く構造を解消し、同じ業務定義を異なる申請に使える。

## RF-08 Temporalアダプタの境界を整理する

優先度：通常。依存：RF-06、RF-07。

- [ ] 同期Engineをasync Activityから呼ぶ現在の方式を見直し、Workerのイベントループを長時間ブロックしない実行方法を選ぶ。
- [ ] 再試行しない業務エラー、一時障害、契約不整合を区別してTemporalの失敗へ変換する。
- [ ] Workflow ID、Run ID、Activity ID、業務実行IDの対応を共通化し、文字列置換による衝突を避ける。
- [ ] Temporal側の再試行とパイプライン側の再試行の責任を明示し、回数を勝手に増やさない。
- [ ] Worker・サーバー・イベントループの起動停止をテスト用の管理クラスへまとめ、途中失敗でも後片付けする。

完了条件：既存の待機・Worker再作成・重複Signal・Timer・Child Workflow・却下の試験が通り、保証範囲が拡大したと誤認させない。

## RF-09 受入モデルとpytest連携を分離する

優先度：高。依存：RF-01、RF-02。

- [ ] Case、操作の説明・参照、Gherkin読取りと検証をpytestの実行登録から分離する。
- [ ] pytestプラグインに、対象シナリオ・契約・アダプタを設定で渡せるようにする。
- [ ] tests/conftest.pyから購買固有の読込み・選択・結果収集を移し、購買fixtureと変異注入をサンプル側へ限定する。
- [ ] stacklevelや_pytest_bdd_exampleなどpytest-bddとの結合箇所を一箇所に隔離し、互換性試験を持つ。
- [ ] 空の検証を拒否する方針、シナリオID、Outlineのcase ID、未定義操作の検査を維持する。
- [ ] 受入機能を使わない利用者は、pytestだけでコアのテストを動かせる構成にする。

完了条件：購買サンプルをimportせずにライブラリのコアを検証でき、別の業務にも同じ受入ツールを接続できる。

## RF-10 文書生成とコード生成を整理する

優先度：通常。依存：RF-01、RF-09。

- [ ] ドメインモデル、検証、Markdown描画、型・骨格の生成を分ける。
- [ ] 購買専用タイトル、リンク先、featuresディレクトリを引数または設定にする。
- [ ] Markdownエスケープ・アンカー・固定IDの対応表を共通化する。
- [ ] 業務概要、型、実装対応、受入条件の生成入口を整理し、利用者がどのコマンドを使うか迷わないようにする。
- [ ] 生成と--checkを共通の比較処理にし、複数ファイルの生成途中失敗による不整合を避ける。
- [ ] 手書きの契約・実装・featureを上書きしない制約を維持する。

完了条件：同じ定義から決定的に生成でき、業務名・配置場所が違ってもリンクが成立する。生成パス変更は明示的に移行する。

## RF-11 結果レポート・ハッシュ・テスト構成を整理する

優先度：通常。依存：RF-09、RF-10。

- [ ] 結果JSONへschema_versionを付け、読込み時に構造・ケースID重複・状態・必須項目を検証する。
- [ ] 手書きのファイル一覧に依存したハッシュを見直し、対象・除外・設定・依存バージョンの扱いを明示する。
- [ ] 仕様文書、ある実行の結果、現在の定義に対する過去結果を引き続き区別する。
- [ ] コア単体、保存アダプタ、業務受入、Temporal結合、変異試験の配置・マーカー・実行コマンドを整理する。
- [ ] 全ケース未実行、フィルタ実行、スキップ、準備／後片付け失敗、収集中断のレポートを試験する。
- [ ] 任意依存がない最小環境と、Temporalを有効にした環境のCIを分けて確認する。

完了条件：不正・古い・未実行の結果を合格に見せず、実際の実行とレポートを追跡できる。

## RF-12 第二の小さな業務で境界を検証する

優先度：通常。依存：RF-04〜RF-11。

- [ ] 購買用の型・Services・タイトルを使わない、別の小さな業務を一つ定義する。
- [ ] 契約、実装、ロール、トリガー、受入featureを利用側で追加する。
- [ ] ライブラリ本体へ業務名や個別ファイルを追記せず、生成・実行・受入検証を行う。
- [ ] ID改名、入力追加、シナリオ追加で、どこを手書きしどこが自動反映されるか確認する。
- [ ] 旧import・既存サンプルの移行案、公開API、任意依存、実行手順を更新する。

完了条件：別業務の追加に本体コードの購買固有変更が不要で、リファクタリングの目的が利用側から確認できる。

## リファクタリング後の拡張タスク

以下は責務分離と同時に実装済みと扱わない。

### EX-01 PostgreSQLのロックとトランザクションを検証する

依存：RF-04、RF-05。

- [ ] トランザクション単位の排他か、セッション単位の業務ロックかを用途別に選ぶ。
- [ ] ロック専用接続、接続プールへの返却、明示解放、切断時の解放を設計する。
- [ ] 複数プロセス・Workerで同じキーを競合させ、異なるキーの並行実行も確認する。
- [ ] 切断でロックが失われても外部副作用は止まるとは限らないため、一意制約・冪等性・必要に応じた所有権確認を組み合わせる。

完了条件：実PostgreSQLでキー単位の排他と失敗時の挙動を確認できる。SQLiteのBEGIN IMMEDIATEはDB単位の書込み制御であり、同等品とは扱わない。

### EX-02 実S3アダプタを検証する

依存：RF-05、RF-06。

- [ ] 実行専用キー、バージョン・所有者の確認、曖昧な成功、再試行、補償を実APIで試験する。
- [ ] 模擬保存の結果と、AWS上で確認した結果を分ける。

完了条件：削除対象外の物を消さず、応答消失・補償失敗の残存物を追跡できる。

### EX-03 自動復旧・認証・長期運用を拡張する

依存：RF-06、RF-08。

- [ ] Activity途中停止、キャンセル、タイムアウト、実行履歴の移行・バージョニングを扱う。
- [ ] 認証済み受付と実組織のロールを接続し、未信頼のSignalやpayloadを直接Principalにしない。
- [ ] 実行中の処理との競合を避けた復旧と、監視・運用手順を整える。

完了条件：追加した保証ごとに、正常系だけでなく障害注入と復旧の証拠を残せる。

## 全体の完了条件

- 固定ID、受入条件、業務の結果、補償の対象範囲を維持する。
- コアが購買サンプル・SQLite・pytest-bdd・Temporalへ不要に依存しない。
- ロック・保存・履歴・受入アダプタの責任と保証範囲が明示される。
- 同じ契約・シナリオから型・文書・実行の対応を再現できる。
- モジュール名などの変更に伴う生成差分と、業務上の変更を区別できる。
- 顧客レビュー、リモートCI確認、外部基盤の未検証事項を残したまま、全保証済みと報告しない。
