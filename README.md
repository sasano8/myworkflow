# myworkflow

Python 3.14向けの、コードに宣言した業務契約から概要ドキュメントを生成するプロトタイプです。外部依存はありません。

## 実行

リポジトリ直下で実行します。

```sh
python3.14 -m examples.approval
python3.14 -m unittest discover -s tests -v
python3.14 -m examples.approval > /tmp/approval.md
diff -u examples/approval.md /tmp/approval.md
```

宣言例は [examples/approval.py](examples/approval.py)、レビュー用の固定出力は [examples/approval.md](examples/approval.md) にあります。GitHub ActionsでもPython 3.14でテストと出力の完全一致を検証します。CI自体の実行はpush後です。

## モデル

- `Workflow`: 業務上のまとまり。
- `Binding`: パイプラインの配置・起動定義。トリガー、入力元、先行配置、待機・再開条件、次ワークフローを宣言します。
- `Pipeline`: トリガーから独立した、入力・出力・応答有無とステップの契約。
- `Step`: 業務名・概要とアーティファクト操作を宣言します。
- `Lock`: コンテキスト上のアーティファクトをキーとして参照する排他契約。範囲・競合動作も出力します。
- `Artifact` / `Use`: 情報の識別と、参照・保持・DB読取・DB作成・DB更新・送信の区別。

受付・返却行は描画時に契約から生成します。途中のステップにリクエスト／レスポンスを持たせません。入力と出力は同じ列、過程のアーティファクト操作は別列です。

固定IDはコードに明示し、名称・順序から生成しません。同じパイプラインを流用すると定義IDは共通で配置IDが異なります。出力行の固定IDはワークフロー／配置／パイプライン／ステップのIDを組み合わせます。IDに `/` を含めない命名を推奨します。表示連番のみ宣言順に採番します。実行IDは未実装です。

## サンプルで確認できること

申請受付 → 承認イベント待ち → 承認反映 → 指定日時待ち → 次ワークフロー起動の契約を表現します。実行開始パイプラインを手動実行でも流用しています。引継ぎ先の「申請実行」は参照先だけを示す空のワークフローで、実行内容は未定義です。

テストは保存済み出力との完全一致、配置による流用、改名・並べ替え時のID維持、不正参照・不整合な入出力契約の拒否、表のエスケープ、待機・排他・応答不要の表現を検証します。固定出力の更新は生成後に差分をレビューして行います。テスト中に期待値を再生成しません。

## 今回の範囲と設計上の未決事項

これは宣言・検証・ドキュメント生成のプロトタイプです。HTTP受付、ステップ関数の実行、DB操作、ロック、永続化、イベント配送、スケジューラは実装していません。次ワークフローの起動も宣言だけです。

入力元、トリガー、待機条件は現時点では説明文字列です。入出力のPython型・スキーマ、条件分岐、期限切れ、再試行、冪等性、遷移の循環検証、コンテキストの読み書きのデータフロー検証は今後の対象です。たとえばロックのキーが既知のアーティファクトかは検証しますが、実行時にコンテキストへ格納済みかはまだ検証しません。実行エンジンへ発展させる前に条件を構造化する必要があります。

自然言語要件からの骨格生成はまだ実装していません。まずこの宣言形式と出力表を使って表現力を確認し、その後にAIによる骨格生成の入力・出力契約を定めます。docstring／デコレータによる実装関数との関連付けも今後の対象です。

## GitHubでの表示

ワークフローとパイプラインの名前は見出しにまとめ、各配置を個別の表で表示します。トリガーは独立列の受付行に表示します。固定IDは表の独立列に表示します。

同じ配置に複数の起動経路を持たせる場合は `Binding.additional_triggers` に `Trigger` を追加します。受付行はトリガー1、トリガー2として同じ連番で表示し、後続ステップを一度だけ出力します。各トリガーは入力元・先行配置・待機条件を個別に持ちます。既存の受付IDを維持し、追加受付にはトリガーIDを付けます。別の配置やワークフローの流用は自動的にまとめません。
